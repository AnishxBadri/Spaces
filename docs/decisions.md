# Decision ledger

Every decision with its current answer and the reason for it. An amended decision reads as it stands now; a superseded one is folded into the decision that replaced it. Git holds the history, the options weighed and the dates. Numbers are stable: other docs cite them.

How the system works is in `docs/architecture.md`; ideas not yet decided are in `docs/considerations.md`.

## Foundations

- **D88 · TanStack Start, not Next.js.** One data model (TanStack Query plus server functions), typed search params for saved views, plain Node output, the worker as a second process. _Why:_ an authenticated, client-heavy app gains little from server components and pays their boundary on every component. Not relitigated without new information.
- **D89 · Plugins leave the image.** Integrations install at runtime into `./data/plugins`, run only in the worker and write only through ports; plugins feed the graph and never extend the product. _Why:_ compiled-in vendors cost every box image bytes, attack surface and migrations, and baked vendor names into shared enums no third party could migrate.
- **D90 · Lists are views; records are unique.** A list is a saved filter over one object's records and holds no values or membership; anything worth saying about a record is an attribute on it; a second pipeline is a second object. _Why:_ an entry engine would be a second value store invisible to history, provenance and the assembler.
- **D91 · A deal is first class.** One deal is one opportunity in one company; a company has many over time. Watching is space tagging, never a stage. Deals close, never delete. _Why:_ each round keeps its own arrival, stage history and pass reasoning, which is the memory an investor pays for.
- **D92 · Spaces own classification.** The litmus test: could I write a memo about it and track companies in it? Then it is a space. Industry and sector never become attributes; cross-cutting is many-to-many tagging. _Why:_ a sector field is the drift vector, and approaches cut across markets.
- **D93 · A tiny seed taxonomy.** A handful of example nodes, no curated ontology, no seed reconciliation. _Why:_ the tree is the investor's vocabulary, and a shipped ontology pre-empts it.
- **D94 · No thesis object.** The mandate is the strategy surface; market claims are notes filed in their space. _Why:_ a thesis's content is prose, which a filed note already carries.
- **D95 · Templates by example.** Saved from a real note, record, space or email; workspace-shared; we ship none; instantiation copies; nothing auto-creates. _Why:_ a shipped template pre-empts the user's vocabulary, and contextual defaults are the first step to workflow sprawl.
- **D96 · Merge repoints at write.** Every entity-referencing column is in `ENTITY_REFS`, which drives merge, delete and context; the loser row stays as a redirect; a snapshot is kept for unmerge. _Why:_ read-time resolution would infect every join forever.
- **D97 · Local storage by default.** Local filesystem, S3 opt-in by env, no bundled object store. _Why:_ a bundled store writes to the same disk, so it fixes nothing, and it makes backup opaque. The one trigger for S3 is an ephemeral host disk.
- **D98 · Several workspaces per install.** Decided, not built: one organization holds N books, the user is the only global object, workspace creation is instance-admin only. _Why:_ one fund keeps separate books; nothing may foreclose a hosted future, so all scoping goes through one choke point.
- **D99 · The hostability contracts.** Six, in `docs/architecture.md` (_Hostability contracts_): the entrypoint owns `./data`, either process dying exits the container, the app never terminates TLS, health checks the database, backup is both-or-neither with rollback by restore, and the required env is frozen at `DATABASE_URL` and `APP_URL`. _Why:_ "compose up works first try" has to stay true five features from now.
- **D100 · Embeddings.** Never forced, automatic once a provider is set; one dimension pinned per deployment (768); changing the model re-embeds everything. _Why:_ vectors from two models in one column are silent garbage.
- **D101 · API tokens.** MCP and `/api/v1` authenticate against one per-user `api_token` table; no OAuth, no external identity provider. _Why:_ `canRead` is per user, and the required env is frozen.
- **D102 · Tasks are not entities.** A plain table with `task_entity`, searchable as a Cmd-K lane; Today is the reminder channel, with no required email. _Why:_ a task is a verb against a subject, and self-hosted mail is optional.
- **D103 · Portfolio scope.** Our position only, never a full cap table; the original currency is the truth and converted values are never stored; fund administration and LP reporting are fenced out; an LP is never a workspace member, and any portal reads published snapshots only. _Why:_ the front office is the wedge; fund admin is another product, and hiding a workspace behind filters is one missed `WHERE` from a leak.
- **D104 · Hybrid data layer.** Route loaders own navigation, auth and route context; TanStack Query owns page data, freshness and mutations (`ensureQueryData` in the loader, `useSuspenseQuery` in the component, `invalidateQueries` by key after a write). Decided, not built. _Why:_ nothing caches requests today: every save re-runs the active loaders through `router.invalidate()`, and TanStack Query serves only a few client fetches. Keyed queries cache page data and refresh only what a write touched.
- **D105 · Deletes are hard; there is no trash.** Documents, terms and notes hard-delete through the registry executor. _Why:_ one deletion model, and "deleted" means the same on every page.

## Graph, identity and provenance

- **D1 · What `source_ref` points at.** Always `integration.id`, FK enforced, null unless `source_class = 'integration'`. Which account's bytes is one hop away through `connection_id`. _Why:_ one enforceable FK, and two integrations sharing a Google grant stay distinguishable.
- **D7 · New entity-referencing columns.** Each gets its `ENTITY_REFS` entry in the same change as the column, with `context` a deliberate null where it is never AI-visible. Plugin schemas never FK `public.entity.id`; they store the uuid and resolve through `merged_into_id` at read. _Why:_ merge repoints from that list, and a plugin FK would block merge.
- **D9 · The same bytes or mail arriving twice.** First writer wins for class, ref and uploader; a dedupe fills any provenance field still null (external id and url, connection, source path) and never overwrites one. _Why:_ the first arrival is the true origin, and later channels only add what it lacked.
- **D59 · Who writes `supersedes`.** A verb does, never a relation picker: "Newer version of…" on a document, "Save as new version" on a note, an optional pick at upload, and a suggestion at intake. Never written automatically; nothing is deleted; the ranker demotes the older item. _Why:_ a wrong `supersedes` hides true facts from the AI, which is worse than a missing one.
- **D60 · A person at a company.** An attribute: people's system attribute `companies`, a multi `record_reference` to companies; `contact_at` is retired. `founders` stays a separate role. _Why:_ one write path gives history, provenance, views and import for free.
- **D69 · Relationships and attribute edits.** A relationship is a pair of `record_reference` attributes joined by `options.inverseOf`, in four cardinalities; the value is stored once on the owning side and the inverse is derived from the `references` links. Edits only widen (single → multi, select → multi-select), logged as one event; narrowing is refused. System attributes are never archivable. Custom objects archive, never delete. _Why:_ storing both sides is the drift `ENTITY_REFS` exists to prevent.
- **D75 · Identity is a unique attribute.** Person `emails` and company `domains` are multi-valued system attributes with `options.identityKey`; `setValues` mirrors each value into an `is_identity` row of `entity_alias`, whose partial unique index enforces one owner per key. LinkedIn is a plain `url` attribute. Role addresses (`ROLE_PREFIXES`) are stored but never mirrored. No country-specific identity keys. _Why:_ views, import, history and the API see identity like any value, and Postgres cannot enforce uniqueness inside a jsonb array.

## Objects, views and lists

- **D2 · Views on a surface with no object.** A `surface` discriminator on `view` (`object | document`) with `object_id` nullable and a check tying them. A surface may carry views when it is a list of rows with a stable id and a declared column registry. _Why:_ an object row carries an attribute registry, and minting one for documents breaks the two-tier model.
- **D5 · The view filter evaluator.** One pure, table-driven condition → SQL builder owned by the views code; other surfaces feed it a column registry. _Why:_ one evaluator, one index plan.
- **D6 · Client and server matchers.** Both stay, and both tests read one shared case table. _Why:_ the table is what keeps them agreeing.
- **D35 · List query state.** Conditions stay out of the URL; the text box is a server ILIKE over the canonical name and name aliases. _Why:_ conditions are large and saved views already persist them.
- **D36 · Sorting and filtering by attribute.** Only attributes flagged filterable or sortable are offered; a saved view whose attribute loses its flag keeps the condition, marks it unavailable and falls back to unfiltered. _Why:_ no silent slow path, and no auto-flagging.
- **D37 · The deals board.** Never paginated: all open-stage deals load, closed stages collapse behind a count. _Why:_ a board is read whole.
- **D106 · A list and a record are fixed panes.** On a list page the head never folds and the page never scrolls. Under the head and the tabs, the table's card fills the window at one size whether it holds three rows or three thousand. Rows scroll inside the card, the column head holds its top and the foot holds its bottom (`n of total · Load n more` left, `n more columns →` right). Columns fill the card's width, then scroll sideways with the name column pinned. The search box ends on the card's right edge, and a row's `···` stays pinned right while the columns scroll. A tabbed record page (company, person, deal, custom object) and a space page are fixed panes too: the head never folds, the folder under the tabs runs to the window's foot whether its tab holds one row or three hundred, and each tab scrolls inside it and keeps its own place; the rail beside it scrolls on its own. A tab's empty sections still collapse to their one `Name +` row; the folder, not the section, holds the height. A list falls back to one page scroll below `md`, a record below `xl`, where its rail stacks over the body. _Why:_ the tabs, the count, the head's actions and the row menu never scroll out of reach, a short list or a quiet record reads as short, not broken, and a record's tabs are views like a list's, so moving between a list and a record never changes how the page scrolls.

## Spaces and research

- **D45 · Space-tag suggestions.** The candidate vocabulary is the record's existing space subtrees plus their siblings, capped at 40 nodes. _Why:_ the whole tree is noise for a model.
- **D71 · Space structure in AI context.** The assembler gives position (each filed space's full path), peers (a capped set of companies in the same leaf), and, when a space is the subject, its subtree with counts, memos, companies by stage and terms. All of it is ranked and capped and passes `canRead`; a sensitive space anywhere in a path keeps the call sensitive. _Why:_ answers need the map, not only the memos.
- **D72 · Space watches.** Research engines attach to spaces, not records. Integration roles are enrich, monitor, discover and research, all ways of using ports. A `watch` trigger runs once per `space_watch` row (host state: settings, nullable cadence, a plugin-owned cursor, run log). The read-only `Spaces` port hands the space brief; the `Discover` port hands back candidates, which become `add_record` or `file_record` cards; dismissals are permanent per (space, domain). Space gains `criteria`. A card never creates a deal. No workflow builder. _Why:_ a space is what a webset is: a definition, a growing set and monitoring.
- **D73 · Spaces are malleable.** Rename, move (reparent, refused under its own descendant) and archive (hidden, filings kept, watches paused, never deleted). Split is create-child-then-move; merging two spaces is deferred until two collide. Filings never change on their own; watches and dismissals follow the space by id. The space page reads like a record: a `···`-only head, Overview first (readouts, What's moving, open tasks, latest companies), then Companies · Notes · Files · People · Records; the rail is Criteria, Watching and Map. Archive asks nothing because Restore undoes it. The crumb is the path; counts live in the tabs and Overview's readouts, which replaces D48's crumb count line. _Why:_ structure emerges from encounter, and a tree that cannot be corrected makes that false.
- **D77 · Exa.** The open web as host jobs: Find (in Ask, results as a table checked against what is held), Watch (D72), Research (signals and one cited brief on a record), and an optional enrichment source. Save as watch needs a space and carries the turn's results; untouched rows become cards. One open card per (space, domain), so later finds append evidence. A sensitive scope never reaches Exa. _Why:_ Apollo is a directory, Exa is a search engine; finding matters most.
- **D87 · Feeds are first class and built in.** A Feeds page in the Library group (`G R`) with two tabs, Headlines and Sources, and a space filter beside them. Headlines is a list beside a reader: a story is the source (logo, name, time), the headline, two lines of summary and the item's photo when it carries one; the reader shows the feed's own text, cleaned and capped, then `Continue on <site> ↗`, and never fetches the article page. Sources is a table of feeds; a failing one marks the Sources tab and its `Fix ›` reopens its window. Add feed asks for a URL and spaces only: a site address is resolved to its feed, and the name comes from the feed. The worker fetches every feed every 30 minutes and keeps 90 days of headlines. A feed is tagged to spaces: at most two of its headlines show in each space's What's moving, the rest behind `Headlines ›`, and the feed is one more row in the Watching lane. Today shows one line at most. Workspace-wide, no read state, no company matching. Logos and item images are fetched and stored by the worker as photos, never hotlinked. Feeds have no Settings entry. `plugins/rss` retires with no migration, the SDK drops the `feeds` role (an SDK major) and the Plugins catalogue loses its Feeds group. Drawn on the Paper Feeds page, boards 01–05. Supersedes D33 and the feed clause of D72. _Why:_ a feed needs no key, account or credits (D76's Website-source reasoning), a plugin cannot draw the page it needs, and a reader keeps the skim on the page while the article stays the publisher's.

## Notes, documents and storage

- **D32 · Deck links.** No headless browser, no renderer port, no snapshot container. A DocSend or Pitch link stays a link; a PDF response is filed and an article is clipped. _Why:_ ~400 MB of Chromium breaks the hostability contract for a capability that is unreliable even when it works.
- **D38 · Retention of derived layers.** Derived layers are sha-keyed caches under a size budget (default 2 GB), LRU-evicted, rebuildable, and absent under `retain: text`. Authored inputs are records: an import payload follows `retain: full` for 90 days, then text; `import_batch` and `import_row` stay until reversed or pruned. _Why:_ the per-row receipt is what makes a batch reversal legible.
- **D66 · Linked storage.** No user-made folders; a linked folder shows its own provider tree, read-only. Native Google files open in Google and default to `retain: text`. App delete never touches the provider ("Remove from record"); unlink deletes only the copies that came through the binding, after a counted confirm. One connection per Google product, keyed by `(user, provider, product, external_email)`. Least-privilege scopes: Drive `drive.file`, plus `drive.readonly` only for a bound folder; Calendar `calendar.events.readonly`; Gmail `gmail.readonly` and `gmail.send`; never full `drive`, `mail.google.com`, `gmail.compose` or `gmail.modify`. A record's Files tab: one add row, our files grouped by kind, a bound folder as its own band, then the attachments nobody filed by hand as a folded `From email` band (D110), every row ending on a state word. _Why:_ a founder's data room is not ours to delete, and disconnecting Gmail must not revoke Drive.
- **D83 · Note kinds.** Two: Note and Memo. A memo pins to the top of wherever it is filed, can be a space's face and has its own tab. _Why:_ a kind must change presentation or intent, and `scratch` did neither.

## Email, meetings and arrival

- **D28 · Outbound delivery.** No outbound webhooks. The read API has a `?since=` cursor so polling is cheap and correct; a digest, if built, sends through the optional `SMTP_URL`. _Why:_ outbound is a subsystem nobody has asked for; the cursor is the part that is expensive to add later.
- **D30 · Mail bodies.** A body is a note through `interaction.note_id`, so mail uses note visibility; /notes leaves mail-born notes out by default. Synced mail is private to the mailbox owner; forwarded mail is born shared (D49, D67). _Why:_ one visibility model, and the private-note carve-out is already enforced in SQL.
- **D31 · Forwarding transport.** IMAP poll of an operator-owned mailbox. _Why:_ the only option inside the frozen required-env set.
- **D34 · Participants.** Every visible participant becomes a person, except that a shipped free-email-domain list never mints a company. A meeting becomes an interaction when it touches the graph (an attendee or the title resolves to a record). _Why:_ people are cheap to merge; junk companies are not.
- **D49 · A deal's threads.** Derived: every thread edged to the deal's company or one of its contacts, past and future. One explicit edge to a deal (pin or exclude) is the only manual act. A reply inherits its thread's edges. A forward is parsed for its Forwarded-message block. _Why:_ nothing about a deal is known at arrival, and per-thread attaching does not scale.
- **D67 · Email.** Store the email: `headers`, the raw MIME as a blob, HTML rendered sanitized in a sandboxed iframe, inline `cid:` images shown, remote images never loaded. Attachments are documents joined to the email, carrying their own visibility; filing a private attachment does not widen it; their bytes stay in Gmail until a person keeps them (D110). Privacy has three layers: synced mail private to its owner, a per-record override, per-email grants; subject, participants, date and owner always show. Summary and labels are derived display text, never proposals. Interaction stats (first, last, next) are a derived table. Drafts are local, author-private `email_draft` rows with To, Cc and Bcc. Sending goes through the Gmail plugin with `gmail.send`. Templates gain an `email` kind; variables are paths (`{{company.name}}`). Deferred: scheduled sends, mass sending, sequences, signatures. _Why:_ the body note stays the one searchable text; everything else is display.
- **D68 · Meetings.** A meeting is an interaction (`kind: meeting`), never a record. Calendar sync updates the row in place by iCalUID; a cancelled meeting is marked, never deleted; RSVP is shown, never edited. Linked records are `interaction_entity` edges. Prep runs the assembler over the linked records on demand, with Save as note. A Meetings list page sits in the Library group (Upcoming, Past with no-write-up first). Recorders are plugins: they hand match keys to `Content.logInteraction` and the interaction writer attaches to the calendar meeting or births a `call`; a transcript is a document, a recording stays a link, action items are task suggestions. _Why:_ one meeting is one row, whatever wrote to it.
- **D78 · Recorder notes.** A recorder (Granola first) is a personal key-based connection polled on a schedule. The member ticks folders; a note in a ticked folder is shared, a note outside one is never fetched, and moving or deleting it removes our copy. The enhanced note becomes the write-up when there is none, else a second shared note. Raw typed notes and the transcript are opt-in and private to the member. A note a person filed from their tool is set in serif with "via <tool>"; unchosen AI text stays sans. _Why:_ the folder is the share decision, as forwarding is for mail.
- **D112 · Meetings and calls.** The Meetings page is a fixed pane (D106) with two folder tabs, `Upcoming` and `Past`, a person chip that reads `Mine` by default and picks any members or `Everyone` (absent in a one-member workspace; a member's meetings are those they organised or were invited to, and the `No write-up` band follows the chip), and `Log interaction` (`L`) as its head's primary, opening on Call with `Who was involved` required. An admin reads nothing more than a member: `canRead` has no role override, so a private write-up stays its author's. Upcoming groups by day on bone bands, one line a meeting: the calendar icon, the time, the title (a linked record's name before it in graphite when the title names none), the people (H2, no answer marks) and a `···` with Prep, Join call and Google Calendar; `Join ↗` shows at rest only while the meeting is live or starts within 10 minutes. Past opens with a `No write-up n` band, then week bands; its rows are thread rows (D109), calls among them, the second line the write-up's summary led by the recorder's mark when one wrote it. A meeting with a recorder connected among its attendees counts as unwritten only an hour after it ends. Prep lives only in an upcoming meeting's window, in the column the write-up later takes: a cited brief (who is coming and who is new, the deal's stage, the last write-up and open tasks, what moved since) with `Ask about this`, `Done` and `Save as note`; it never runs unasked. `Write it up` opens the note window over whatever page it is pressed on (D108). Action items are read once from every shared write-up, a person's or a recorder's, and are decided in the meeting window and in Today's Needs you under Tasks; an accepted one is the write-up author's task. Calendar sync reads each connected account's primary calendar and keeps an event only when it is timed, of Google's default type, not private in Google, not declined by its owner, and has an outside attendee not on the account's exclude list; internal meetings are logged by hand. `Remove from Spaces…`, offered to the meeting's attendees and to admins, takes out a meeting or its series and is remembered. On Today, Write-ups follow `Mine` and the grace hour, the day strip's head names the next meeting (`Meetings 4 · next in 45m`) and its head shows `Join ↗` only near a call. A record's Interactions tab opens with an `Upcoming` band (the next three, day and time, the rest folded), `This week` holds only what happened, and the `Next meeting` readout opens the meeting. Other recorders and any dialer are plugins on `Content.logInteraction`, built when asked; there is no calendar grid, and object lists keep `mine` as a saved view, not a chip. _Why:_ the page answers what is next and what is owed, the window is where a meeting is acted on, and a grid of the meetings Spaces keeps would show free time that is not free.

## AI

- **D4 · Citations.** One ref grammar for every citation; a chunk ref is `<kind>:<entityId>#<idx>`. Refs resolve through `merged_into_id`, and a deleted target resolves to a tombstone. _Why:_ the suggestion table is a second persisted writer of refs, and a user reads it.
- **D10 · MCP and sensitivity.** Every MCP read tool applies the same sensitivity check as `complete()`: a sensitive subject returns its existence and a typed refusal, never its content. _Why:_ an external agent is one more egress.
- **D11 · Sensitive embeddings.** Sensitive chunks embed only through a local provider; local embeddings are Ollama only, with no in-process model. With no local provider, sensitive records get no vectors. `embed(input, { sensitivity })` carries the sensitivity. _Why:_ refusing is the doctrine; an in-process model adds ~44 MB plus a web↔worker seam to buy only the step of running Ollama.
- **D20 · The routing grid.** A ledger, one row per lane, with a default and a sensitive provider cell. _Why:_ no new pattern for one table.
- **D23 · The semantic lane in Cmd-K.** A second wave: lexical first, then the fused query re-run with vectors 600 ms after the last keystroke, suppressed once the user has moved the selection or pressed Enter. _Why:_ no row moves under the cursor.
- **D24 · `kind: 'other'`.** Means unknown. The classify lane proposes once per document and a rejection is remembered. _Why:_ a human's "other" and a default "other" cannot be told apart.
- **D41 · AI in front of a human.** An AI proposal that would write with no human present becomes a `suggestion` row. A guess shown on a screen a person is already confirming (an import column mapping) is a pre-selected control, not a suggestion; committing is the confirmation. The import batch records which mappings the AI proposed. _Why:_ the wizard stays one screen, the preview catches a wrong mapping before commit, the batch void (D12) undoes it after, and the batch keeps the provenance a suggestion row would have.
- **D44 · Suggestions on a record.** A read-only Waiting count on the rail, opening Review filtered to the record. _Why:_ decisions are made in Review and Today, not in a chip.
- **D46 · Caps and usage.** Daily tokens are the one unit, with a workspace ceiling and one per integration. No bundled price table; an optional operator-entered $/Mtok per provider turns tokens into a labelled estimate. A cache hit writes no `ai_usage` row but opens an `ai_run` with a cached step. _Why:_ one unit the operator can reason about.
- **D58 · The assembler in core.** A narrow `SimilarLane` service in core; the live Layer stays in apps/web beside the embedding pin. _Why:_ moving the embedding stack into core would drag the provider stack across the worker fence.
- **D70 · Find and Ask.** Cmd-K finds and goes; Ask answers. Cmd-K groups Jump to · Actions · Records (lexical and fuzzy, so a typed name wins) · Passages (the semantic lane as places to go); it is one fixed size with an always-mounted preview pane; nothing typed shows the page's own actions only. Tab or ⌘J hands the query to Ask: a docked, closable, resizable panel and an `/ask` page over one thread store. Ask is an in-process MCP client with the same tools as external agents, plus `query_records` and portfolio tools so counts and money are computed. Answers cite every claim and are set in sans; action cards propose, and undecided ones wait in Review; threads are private and not entities. What a turn read is frozen with it; an answer whose source the asker can no longer read is hidden. _Why:_ split by the question, not the technique, with one set of tools and rules.
- **D76 · Enrichment is a host capability.** The host owns triggers, rules (fill blanks only, a cleared value stays cleared, a disagreement with a person goes to Review), the where-from popover, credits and egress. A source answers in a host-owned vocabulary (`company.headcount`…); the link lives on the attribute, so there are no `Apollo …` fields. Sources run in the owner's order, free first: the built-in Website source has a markup half that needs no model and a model half that needs an Extract route. Auto-enrich is the Enrich button pressed for the owner on chosen triggers, never for sensitive records outside local sources, parked at the daily cap. Writes are quiet: one Review card per record, one timeline line. _Why:_ Spaces owns no data; every value comes from a source the owner points it at.

## Records, surfaces and settings

- **D61 · The review queue.** Called Review, at `/review`; `/inbox` and `/dedupe` redirect to it. Internal names stay. _Why:_ "Inbox" reads as mail.
- **D74 · The record body.** A rail left (the attribute grid and the relations, each empty relation one `Name +` row) and tabs right: Overview · Notes · Interactions · Files · History. Overview is first and the default every time, and holds the readouts that have a value, open tasks, the latest threads and files. Empty tabs stay visible in graphite with no count. Context is not a tab: it shows on Ask's answer card, with pin and exclude on row menus. Deep links: `?tab=`, `?modal=email&id=`, `?modal=meeting&id=`. _Why:_ Interactions and Files are whole views and fight for one scroll when stacked.
- **D79 · Today is the one attention surface.** Head: the title and the day. A day strip only with a connected calendar. Notices (things that stop the machine), then Needs you (one urgency-sorted ledger with a kind lane, filtered by a Segmented; proposals decided in place; duplicates included), then today's Meetings. Rail: Portfolio and What's moving. Readouts show non-zero figures only and filter the list. Accept, dismiss and apply hold the write for 5 s behind an Undo toast. _Why:_ each source keeps its page; Today ranks them.
- **D80 · First run without a checklist.** Demo data is offered with Start empty as the primary. Today's empty state offers three ways in (import, a deck, a company). Each feature names what it needs in place. Settings › General › Setup is one passive list, rows not set up first, not drawn at 7 of 7. _Why:_ a checklist nags and front-loads setup before need.
- **D81 · Settings by whose it is.** Groups You · Workspace · AI · Integrations, with Integrations = Connections · Plugins · Enrichment · Email forwarding. Toggles apply at once; typed fields collect in one Save bar. `sensitivity_default` is a floor at the top of AI › Models. Accounts group by job, over one connection per provider product (D66). Every plugin and account has its own page; Disable and Uninstall sit in the plugin head's `···`. Plugins is a catalogue grouped by job. Confirms only on actions that break something outside the page. Members see admin pages read-only. Group heads are plain nouns; empty cards are not drawn. _Why:_ settings hold personal, workspace, AI and plugin state side by side, and every page should behave the same.
- **D82 · Bundled providers.** Gmail, Google Calendar, Google Drive and Box are bundled plugins: shipped in the image, always installed, never uninstallable, enabled per use on the provider's page, absent from the Plugins catalogue. Boot installs or upgrades them before `SPACES_PLUGINS`, never fatally. An unsigned bundled tarball is accepted from `bundled-plugins/` only. _Why:_ the SDK seam and `source_ref` provenance stay, and nobody has to install Gmail before connecting mail.
- **D107 · A document scrolls as a page.** A list and a record are fixed panes (D106); a note and a settings page scroll as one page. The head scrolls away and folds into the 48px bar, which keeps the title, the save word and the `···`; the rail beside the body stays pinned under the bar and scrolls on its own only when it is taller than the window. _Why:_ a document wants the window's own scroll, so find, page keys, scroll restoration and the editor's drag auto-scroll behave as the browser means them to, and a page meant for reading never holds two scrollbars.
- **D108 · What a record's tab opens, opens over the record.** An email, a meeting and a note opened from a record's tab open in a window over it (`?modal=email|meeting|note&id=`), its row on bone behind; Esc or Done returns to the same place in the tab. The note window is large (about 900px by the window's height). Its head is the leading mark (a menu: Note or Memo), the serif title, and at the right the people and the day, all on one centre line; never the kind as a word. The foot says `Saved` and, only when the note is private, `Only you`, then `Open as page ↗` and `Done`; it autosaves, so there is no Cancel. A note leads on one mark, in rows and in the window alike: its kind icon, or the recorder's own logo when a recorder (Granola) wrote it; never a calendar, and never a second mark further along the row. A tab's create action is the split `New note ⌄` (templates in its menu) at the right end of the tab's toolbar row, never a full-width row; the toolbar's left holds the tab's segmented filter, as Interactions does. A new note is born filed on the record and opens in the same window. The Notes list keeps opening the note page. _Why:_ reading something about a record should not lose the record, and an email already worked this way while a note jumped away.
- **D109 · An interaction reads in its row, its window, and one log.** A thread row's first line is the kind icon, the subject and its message count, the people (`Priya Raman, Dev Shah +2`) and the day; its second line is the summary, two lines at most in the Interactions tab and one elsewhere, with the clip and its count at the line's right end under the day. A thread with files and no summary prints the file names on that line, so the clip always sits in the same place. The email and meeting windows follow D108: the kind icon leads the head at 20px, and the foot is `Done`; the email window adds `···` for the thread (Open in Gmail, Copy link, File on a deal…, Who can read this…, then Unlink) and `Reply`; its foot note says who reads the email only when that is not the default, so your own private mail carries none and a widened one says `Shared with the workspace` or `Shared by Priya Raman`, while `Who can read this…` holds the full state. An email thread is a column of message cards on the bone ground, 8px apart: each card's header is the sender and who it went to, written one way everywhere (`Dev Shah → you, cc Priya Raman`, `You → Priya Raman`, the address a tooltip on the name; `you` first among recipients and absent when you were not on it) and the stamp. Past three recipients the line counts the rest (`→ you, Dev Shah, Rohan Gupta +2 · cc 3`, a folded card `→ you +7`), and a click on it opens From, To, Cc (and Bcc on your own) on bone under the header; a folded card adds a preview and its clip, and unfolds in place on a click, the newest open; an open card holds its body, quoted history and footers folded to a `···` chip, and, under a rule, its files as cards (the page glyph, the full name wrapping to two lines, the size in mono, a `···`); an open card's header ends on its own `···` (Reply, Reply all, Forward from this message). `Reply` grows the draft as the last card, in ink (Reply, Reply all or Forward, To, Cc, Subject, the body, Attach, Template, Variable), the message it answers folded above, and the foot turns to `Cancel` and `Send`. An attachment opens the file viewer as a second window, stepped down so the thread's head stays in view, its foot stepping through the message's files (`‹ File 1 of 2 ›`) and ending on `Done` back to the thread. The meeting window is the note window's width with two columns: the write-up and its action items on the left, a bone rail on the right with Participants (a name and a ✓ or ?, the answer and address in a tooltip, `Google Calendar ›`) and Records (`Pin a record…`); the head already gives the day and time. Logging is the head's `Log interaction` (`L`), never a second button in a filled tab: Call or Meeting (the tab's filter picks it), About, When, Who was involved, an optional Summary that becomes the row's second line, and `Write it up next`. A logged row lands on bone at the top of its week with a `Call logged · Write it up` toast; with `Write it up next` the note window opens over the record (D108). An empty Interactions tab is its toolbar with `No interactions yet` and `Log interaction`. _Why:_ the clip lane was empty on most rows, a one-line summary hid what happened, an email thread read one message at a time, a sender line said `To Priya Raman` on one row and an unlabelled name on the next, and the meeting window spent its first 300px on who came before the write-up.
- **D110 · An email attachment's bytes stay in Gmail until a person keeps them.** Every attachment is a `document` row joined to its email (`interaction_document`), with the Gmail connection and attachment id as `connection_id` and `external_id`; the worker fetches it once to extract text, chunks and vectors, then drops the bytes, so `blob_sha` stays empty. Opening or downloading fetches through the connection. The bytes are kept only when a person files the attachment by hand (File on…) or picks `Keep a copy`; the automatic filing on the participants' records does not count, nor does accepting a newer version. The stored raw MIME (D67) keeps its headers, text and HTML parts and inline `cid:` images, and drops each attachment part's body, so an attachment is never stored twice. Calendar invites and images under 50 KB never become documents. A disconnected mailbox flips its rows to `external_status: gone`: the text stays, the row says `Gmail disconnected`, and the viewer opens the text. On a record's Files tab, attachments nobody filed by hand sit in a folded `From email` band at the end with its own count, outside the tab's count; filing one moves it into its kind band. _Why:_ copying every attachment stores invoices and logos nobody opens, while a pointer alone loses search, Ask and filing, and dies with the mailbox; text for all and bytes for what the fund chose keeps both.

## Design

- **D18 · Documentation canon.** Reasoning lives in the human document; an operational artifact is derived from it and never argues. `apps/site` reads `docs/*.md` at build time and never forks them. _Why:_ two documents describing one rule is how they drift.
- **D19 · Icons.** One icon per verb, IBM Carbon first (`@carbon/icons-react`), from the one shared icon list (`components/icons.ts`); a custom SVG only for our own concepts, drawn on Carbon's 32px grid with its 2px line and square ends; brand marks only through `ProviderMark`, as the brand's official logo in its own colours. Leading kind icons in rows are graphite; ink is for an icon that is the control or the current state. Every menu item leads with its icon, a service's item with that service's mark (E12). _Why:_ one set read the same everywhere, and Carbon is drawn in the same IBM language as Plex, so its square terminals and flat geometry match the type and the 2px corners where Lucide's round ends did not.
- **D21 · Dark theme.** A re-port, not a token swap; it is not scheduled, and the app is light-only by decision: `:root` declares `color-scheme: light` (so native controls never draw dark chrome on paper), the Toaster takes `theme="light"`, and surfaces stay token-only under `instrument/vocabulary`. _Why:_ bone as a chassis lighter than paper does not survive inversion.
- **D22 · Visual regression.** No snapshot suite. Machine gates are the Playwright functional suite and the vocabulary lint; visual judgement stays human. _Why:_ forty snapshots fail on every intended change.

## Import, export and portfolio

- **D12 · Ledger corrections.** Reversal by compensating event: a void appends the exact negative citing the original; a batch void reverses every event of one batch. No edit or delete path, ever. _Why:_ history stays information, and a bulk import makes "forty wrong rows" possible.
- **D39 · Importer input.** A dialect importer hands core a grid through the `Import` port (`Import.stage`): pre-mapping input that walks the same mapping, preview, commit and batch void as a hand-mapped CSV. The plugin never maps, commits or writes a record; a row that fails decoding fails alone. _Why:_ one commit path, and the batch stays reversible.
- **D40 · An unmapped SAFE.** A bare "SAFE" fails its row, named with the two candidates (`safe_post_money`, `safe_pre_money`). The import maps each such spelling once, or row by row, from the preview; there is no workspace default. _Why:_ a guessed instrument fakes an ownership %.
- **D42 · Export.** A workspace export: a zip of CSVs (one per object, from the registry the import reads), notes as markdown, documents as a manifest plus the blob tree. _Why:_ a user must be able to leave.
- **D43 · Import on Today.** A staged, uncommitted batch shows on Today. _Why:_ a half-finished import is something that needs you.

## Plugins and the SDK

- **D3 · `credential.kind`.** A closed enum; a value is added when the host gains new machinery for a secret, never when a vendor arrives (vendors are `provider` text). _Why:_ the enum names machinery, not vendors.
- **D16 · Signing.** Two schemes: cosign keyless with SLSA provenance for images, a detached ed25519 signature over plugin tarballs checked by the loader. _Why:_ the image verifier is a human with cosign; the plugin verifier is the loader.
- **D47 · Plugin rollback.** "Roll back to <version>" on the integration's row, shown only when the previous version directory exists and no forward migration ran; otherwise the row says restore from backup. _Why:_ the box ships no CLI.
- **D51 · Triggers, not kinds.** A plugin has no kind. Each job declares a trigger (`action` · `schedule` · `event` · `webhook` · `file` · `watch`) and the ports it `uses`, which the admin sees at install and the per-job Layer grants exactly. A webhook's signature is checked by core in web, never by plugin code. A plugin arrives from the registry, an upload or the image (D82). _Why:_ a kind bundled trigger, shape and privilege that are separate questions.
- **D52 · Ports, not returned claims.** A job calls write ports, each of which calls its lane at once and returns what it decided. Claims are the typed arguments of port methods and carry no source or actor. _Why:_ a router would re-derive rules the lanes already hold, and a job could not react to a refused fill.
- **D53 · Cost.** An optional `cost` hook on an `action` job estimates credits; the host refuses before any call when the estimate exceeds the remaining daily cap, and counts spend only from `Receipts.store`. _Why:_ the host owns the cap.
- **D54 · Plugin signing mechanics.** A raw ed25519 signature checked with `node:crypto`; public keys are files in the image named by key id; never read from `registry.json` or env; the private key is a release-workflow secret. The development escape is the marker file `./data/plugins/.allow-unsigned`, off by default, with a boot warning and an "unsigned" badge. _Why:_ no dependency, no network, and the required env stays two vars.
- **D55 · SDK dependencies.** The rule is nothing internal, not nothing third-party: `@spaces/sdk` depends on `effect` and `tldts`, pinned by a test. _Why:_ one domain normalizer on both sides of the port needs the public suffix list.
- **D56 · `Read.search`.** Lexical and fuzzy; a vector lane can arrive later as an injected function. _Why:_ the vector lane would drag the AI stack across the worker fence.
- **D57 · Signal and receipt provenance.** Real columns: `signal.source_class` and `source_ref` with the same check as `entity`, and `enrichment_record.integration_id`. _Why:_ provenance comes from the row, never from free text.
- **D62 · No exit-75 reload.** In-process reload over `NOTIFY plugin_changed` plus an ordinary restart; a worker death still kills the container. _Why:_ a locked hostability contract is not changed for a case first-party plugins do not need.
- **D63 · Plugin actions on a record.** A plugin's verbs sit in the record's `···` as their own group headed by the plugin name, absent while it is degraded, disabled or tripped (Review and Today say why). The outcome is a toast. The host's own Enrich stays a head verb. _Why:_ a record head is `[verb] [verb] [···]` on every kind.
- **D64 · Job status in web.** One shared LISTEN client in web fans `job_status` out over SSE; state on reopen comes from `job_run`, never a missed notification. _Why:_ polling was the latency the plugin spec promised away.
- **D65 · `entity.created`.** Emitted from `resolveEntity` and `createDeal` after the birth commits, never on an attach, and skipped for seed and import births. `autoEnrich` is per integration and off by default. _Why:_ it catches worker-born entities without an outbox table.

## API

- **D8 · The external API.** Built on `effect/unstable/httpapi`, one definition with OpenAPI out; internal calls stay server functions. _Why:_ it ships inside the pinned Effect, and the oRPC bridge was a beta dependency for consistency nobody needed.
- **D27 · API versioning.** One `/api/v1` for every external procedure, plus each payload's own `schema_version`. The URL version moves only when a field changes meaning or disappears. _Why:_ additive changes should not fork clients (`docs/api-versioning.md`).
- **D29 · A public door.** Per-token counters in Postgres enforced in the HttpApi middleware, a documented Caddy rate limit as the second layer, and write-only tokens (a capture token writes and reads nothing). _Why:_ a box may sit on the open internet.

## Hosting and release

- **D13 · Package names.** `@spaces/*` are private workspace names; nothing is published to npm. _Why:_ an internal specifier is not a public identity; the question returns with the first `npm publish`.
- **D14 · Rename depth.** Infrastructure names (compose project, image, role, database) are `spaces`, parameterised in compose so an existing operator can keep old names; the `dealos.*` localStorage keys are frozen. _Why:_ operators read compose files; nobody reads prefs keys, and a shim misfire loses work.
- **D15 · Image tags.** A `core@X.Y.Z` tag publishes `X.Y.Z` and `X.Y` to GHCR and Docker Hub; never `latest`. Upgrade CI covers the window in `scripts/upgrade-tags.sh`. _Why:_ the docs tell operators to pin, and a moving tag would contradict them.
- **D17 · Container runtimes.** Root-then-drop and `user: "1000:1000"` are supported and tested; an arbitrary UID is unsupported but not broken: the entrypoint skips the repair and runs. _Why:_ the entrypoint owns `./data` ownership.
- **D25 · The first duplicate sweep.** Bounded: top 3 candidates per entity and 50 inserts per run. _Why:_ the first run must not flood Review with history.
- **D26 · Worker bundler.** `vite build --ssr`. _Why:_ already installed, and the image ships no source.
- **D86 · Versions by hand.** Three independent lines (core, the sdk, each plugin under `plugins/` outside `_fixtures/`), bumped by `pnpm release:bump` in the commit that earns it; the Tag workflow tags what a push bumped; no changesets, no release PR. The sdk's changelog is `packages/sdk/CHANGELOG.md`. _Why:_ one owner shipping to no outside install does not need the machinery.

## Backend

- **D84 · I/O is Effect.** A module that queries, writes, fetches or enqueues is an Effect program; a pure helper, a type module, a validator shape and client code stay plain. An exported async function is a one-line run of its program. `requireUser` and `requireAdmin` reject with `Unauthorized` and `Forbidden`. Enforced by `effect/io-is-effect`. _Why:_ a server half in each style makes every reader learn both.
- **D85 · Effect Schema is the schema language.** Zod leaves. A server-fn input is `input(schema)`, a validator that throws a readable message; the plugin contract is Effect Schema as SDK 2.0. _Why:_ two schema languages meet at `/api/v1` and `valueValidator`, and each meeting is a bridge to keep honest.
